# Baochip-1x hardware dossier (Linux-port perspective)

Everything below was verified directly in source, not marketing copy. Citations reference:

- **RTL** = https://github.com/baochip/baochip-1x (the actual silicon RTL)
- **xous** = https://github.com/betrusted-io/xous-core (vendor OS; HAL + generated SVDs)

Both are cloned into `sources/` by `setup/fetch-sources.sh`.

## 1. CPU core

Generated by `RTL:VexRiscv/GenCramSoC.scala` (SpinalHDL config → `VexRiscv_CramSoC.v`):

- **VexRiscv RV32-IMAC + Zkn** (scalar crypto via `AesZknPlugin`), 350 MHz, in-order 5-stage.
- Caches: 16 KiB I$ + 16 KiB D$, 4-way, 32 B lines (`cacheSize = 4096*4, wayCount = 4`).
  I-bus is AXI4 64-bit, D-bus AXI4 32-bit.
- **CSRs: `CsrPluginConfig.linuxFull(mtVecInit = 0x60000000)`** → full M/S/U modes,
  medeleg/mideleg, sscratch/stvec/satp — the exact configuration created for Linux-on-VexRiscv.
- **MMU: `MmuPlugin` = Sv32 with hardware page-table walker**, 8-entry TLB ports on I and D
  sides. IO (non-cacheable) address ranges are fixed in hardware: top nibble
  4,5,A,B,C,D,E,F (`GenCramSoC.scala:171-183`). Xous runs S-mode+satp in production
  (`xous:loader/src/main.rs`), so MMU+S-mode is proven on silicon.
- **No PMP. No `time` CSR** (rdtime must be emulated in M-mode or avoided).
- `mtvec` reset value 0x6000_0000 → boot region is RRAM base.
- Debug: 4 hardware breakpoints, JTAG via `DebugPlugin`.

### Interrupt inputs — the critical quirk

`RTL:rtl/modules/vexriscv/rtl/cram_axi.sv:23088-23102`:

```
.externalInterruptArray(cramsoc_interrupt),   // 32 lines, see §3
.softwareInterrupt(1'd0),                     // MSIP can never fire
.timerInterrupt(1'd0),                        // MTIP can never fire
```

There is **no CLINT and no PLIC**. All interrupts, including timers, arrive as *external*
interrupts through the `ExternalInterruptArrayPlugin`, which adds four custom CSRs
(`GenCramSoC.scala:184-189`):

| CSR | Access | Function |
|-----|--------|----------|
| `0xBC0` | M | machine external-irq mask (32 bits) |
| `0xFC0` | M | machine external-irq pending |
| `0x9C0` | S | supervisor external-irq mask |
| `0xDC0` | S | supervisor external-irq pending |

`pending & mask != 0` drives MEIP (machine bank) / SEIP (supervisor bank). The same scheme
is used by linux-on-litex-vexriscv, and Renode's VexRiscv CPU model implements these CSRs.

## 2. Memory map

From `RTL:rtl/verif/utility/daric_defs.sv`, `xous:utralib/bao1x/{core,bao1x_peri}.svd`,
`xous:libs/bao1x-api/src/offsets/common.rs`:

| Region | Base | Size | Notes |
|--------|------|------|-------|
| RRAM (ReRAM, nonvolatile) | `0x6000_0000` | 4 MiB | Memory-mapped reads = XIP-capable; writes only via RRC controller |
| SRAM bank 0 / 1 | `0x6100_0000` / `0x6110_0000` | 2 × 1 MiB | **The only RAM in the system** |
| IFRAM0 / IFRAM1 | `0x5000_0000` / `0x5002_0000` | 2 × 128 KiB | Dedicated DMA buffer RAM for the uDMA subsystem |
| Core-complex CSRs (LiteX) | `0xE000_0000` | 256 KiB | IRQARRAYs, TICKTIMER, TIMER0, MAILBOX… (M/S-visible; top-nibble E = uncached) |
| APB peripherals | `0x4000_0000`… | — | RRC, SCE crypto, DUART, WDG, TIMER_INTF, EVC, sysctrl, AO domain |
| uDMA / IO peripherals | `0x5010_0000`… | — | UARTs, SPIM, I2C, SDIO, I2S, camera, ADC, PWM, IOX, BIO |
| USB device ctrl | `0x5020_0000` | — | Corigine USB 2.0 HS device |

### RRAM partition layout (enforced by boot chain)

`xous:libs/bao1x-api/src/offsets/common.rs`:

| Offset | Contents |
|--------|----------|
| `0x6000_0000` | boot0 — 128 KiB ROM-like root of trust (write-disabled via IFR) |
| `0x6002_0000` | boot1 — 256 KiB USB/UF2 bootloader + recovery console |
| `0x6006_0000` | **payload entry: "loader" or "baremetal" image (this is where our SBI shim + kernel go)** |
| `0x600A_0000 − 768` | (xous kernel slot — irrelevant when a baremetal image spans onward) |
| `0x603D_A000` | end of usable storage (above: security apparatus) |

→ **~3.47 MiB of contiguous XIP flash for SBI shim + kernel + rootfs**, starting at
`0x6006_0000`.

## 3. Interrupt topology

From `xous:utralib/bao1x/core.svd` (LiteX-generated core complex):

- VexRiscv `externalInterruptArray[31:0]`:
  - bits **0–19** = IRQARRAY0–19, LiteX EventManager banks at `0xE0004000 + bank*0x1000`
    (registers per bank: `EV_SOFT`, `EV_EDGE_TRIGGERED`, `EV_POLARITY`, `EV_STATUS`,
    `EV_PENDING`, `EV_ENABLE`; each bank aggregates up to 16 sources; `EV_SOFT` allows
    software-triggered irqs for testing).
  - bit **20** = TICKTIMER alarm, **21** = SUSRES, **22** = MAILBOX, **23** = MB_CLIENT,
    **30** = TIMER0.
- Notable bank contents (full map extractable from core.svd):
  - **Bank 5**: uart0–3 × {rx, tx, rx_char, err} (the uDMA UARTs)
  - Bank 6: spim0–3 events; Bank 7: i2c0–3 events
  - Bank 8: sdio, i2s, cam, adc, filter
  - **Bank 10**: ioxirq (GPIO), usbc, sddcirq, pioirq0–3 (BIO)
  - Bank 2: qfc, mdma, mailbox events, aowkupint
  - Bank 3: crypto done-events (trng/aes/pke/hash/alu/sdma)
  - Bank 13: bus-error irqs (coresuberr, sceerr, ifsuberr, secirq)
  - Many `*_dupe` copies exist in banks 0,1,4,11,14,16–19 (same source, second routing —
    designed so multiple cores/privilege domains can each get a private copy).

**Linux design consequence**: two-level irqchip — (1) a driver for the 32 CSR-based lines,
(2) a cascaded driver for the IRQARRAY banks. TIMER0 (bit 30) and TICKTIMER (bit 20) hang
directly off level 1.

## 4. Timers usable by Linux

| Block | Base | IRQ | Character | Use |
|-------|------|-----|-----------|-----|
| TIMER0 | `0xE001_C000` | ext-irq 30 | LiteX 32-bit down-counter, one-shot + periodic (LOAD/RELOAD/EN/UPDATE_VALUE/VALUE + EV_*) | clockevent |
| TICKTIMER | `0xE001_B000` | ext-irq 20 | 64-bit up-counter, 1 ms ticks (`CLOCKS_PER_TICK` default 800000), msleep alarm | clocksource (+ SBI timer backend option) |
| `cycle`/`mcycle` CSR | — | — | 350 MHz cycle counter | high-res clocksource candidate (needs mcounteren gating check) |
| D11CTIME | `0xE000_0000` | — | "deterministic timer" heartbeat | not needed |
| TIMER_INTF | `0x4004_3000` | via EVC | APB timer (Daric heritage) | not needed initially |
| WDG_INTF | `0x4004_1000` | — | watchdog (`xous:libs/bao1x-hal/src/wdt.rs`) | later: watchdog driver + SBI SRST backend |

## 5. Peripherals relevant to the port

| Peripheral | Base | Linux driver situation |
|------------|------|------------------------|
| **DUART** (debug UART, **TX-only**) | `0x4004_2000` | 4 registers (`SFR_TXD/CR/SR/ETUC`; SR = tx busy) — trivial earlycon/console. RTL: `rtl/modules/core/rtl/duart.sv` |
| **uDMA UART0–3** (PULP-style) | `0x5010_1000`+ | full serial console; requires small DMA rings in IFRAM. Reference: `xous:libs/bao1x-hal/src/udma/uart.rs`. boot1 configures UART on pins **PB14 (TX) / PB13 (RX) @ 1,000,000 baud 8N1** |
| IOX pinmux + GPIO | `0x5012_F000` | new pinctrl+gpio driver. Reference: `xous:libs/bao1x-hal/src/iox.rs` |
| uDMA I2C0–3 / SPIM0–3 / SDIO | `0x5010_9000`+ / `0x5010_5000`+ / `0x5010_D000` | new drivers (phase 5). References in `xous:libs/bao1x-hal/src/udma/` |
| RRC (ReRAM write controller) | `0x4000_0000` | MTD driver for RRAM writes. Reference: `xous:libs/bao1x-hal/src/rram.rs` |
| **Corigine USB 2.0 HS device** | `0x5020_0000` | no Linux driver exists; full Rust reference in `xous:libs/bao1x-hal/src/usb/driver.rs` + boot1. Phase 5, big-ticket item |
| SDDC (SD *device* controller) | `0x5012_1000` | chip can emulate an SD card — out of scope |
| BIO-BDMA (4× PicoRV32 @ 700 MHz I/O coprocessor) | `0x5012_4000` | out of scope (user decision) |
| Crypto (AES/HASH/PKE/TRNG/SCE) | `0x4002_8000`+ | TRNG → hwrng driver is the easy win (phase 5+) |
| PL230 µDMA + MDMA | `0x4001_1000`+ | ARM PrimeCell µDMA heritage; not needed initially |
| AO domain (RTC, wakeup, DKPC) | `0x4006_0000`+ | RTC driver later |

## 6. Clocking

- 48 MHz reference oscillator + fractional PLL (`xous:libs/bao1x-api/src/clocks.rs`:
  `FREQ_OSC_MHZ = 48`, VCO 1–3 GHz, table of common configs).
- Nominal: CPU 350 MHz (spec'd max for TSMC22ULL SKU), BIO cores up to 700 MHz domain.
- boot1 leaves a defined clock configuration (it runs USB HS + 1 Mbaud UART, so clocks are
  sane at payload entry). Phase 4 must read back / document the exact tree the shim inherits;
  `TICKTIMER.CLOCKS_PER_TICK` default 800000 per 1 ms tick implies an 800 MHz reference for
  that counter domain — verify on hardware.

## 7. Boot chain and code signing

`xous:README-baochip.md`, `xous:bao1x-boot/`, `xous:libs/bao1x-hal/src/sigcheck.rs`:

1. **boot0** (immutable): validates boot1's ed25519 signature.
2. **boot1**: enumerates as USB mass storage (`BAOCHIP` volume). Copying a **UF2** file
   writes it to the address encoded in the UF2 blocks. `PROG` button = enter bootloader /
   run image; also a 1 Mbaud serial console on PB14/PB13 with management commands
   (`audit`, `lockdown`, …).
3. boot1 validates the payload at `0x6006_0000` (768-byte signature block: ed25519, length,
   version, anti-rollback) and jumps via plain `jr` — **payload starts in M-mode**
   (`sigcheck.rs:jump_to`, a0 = xous kernel address by convention — ignorable for us).

**Keys**: chips ship accepting four keys, including a **public developer key**
(`xous:devkey/`, private half published). First boot of a dev-signed image irreversibly
increments the `DEVELOPER_MODE` one-way counter and erases factory secrets
(`offsets/common.rs:172`). *Accepted cost for this project (user approved).*

**Tooling to reuse**: `xous:tools-bao/` + `cargo xtask` produce signed UF2s; standalone
packaging template: https://github.com/bunnie/dabao-console. Our `tools/` wraps this for
non-Rust payloads (SBI shim + kernel + rootfs blob).

| Tool | Status | Role |
|------|--------|------|
| **Renode** | No bao1x platform exists, but Renode boots Xous (Sv32 + custom irq CSRs) on the sibling betrusted SoC; xous ships C# models to reuse (`xous:emulation/peripherals/`: `LiteX_Timer_32.cs`, `ticktimer.cs`, `susres.cs`…) | Primary dev loop (phases 2–3): write `bao1x.repl` + DUART/IRQARRAY/uDMA-UART models |

## 9. Board (Dabao)

Minimal: bao1x + USB-C (power/boot1) + `RESET`/`PROG` buttons + two 16-pin headers.
**No external RAM.** Console plan: 3.3 V USB-UART adapter on PB14/PB13 @ 1 Mbaud.
Board design files: https://github.com/baochip/dabao.

## 10. Open hardware questions (carried into later phases)

1. Exact clock tree state at payload handoff from boot1 (phase 4).
2. `mcounteren`/`scounteren` state — can S-mode read `cycle` directly? (phase 3)
3. RRAM read wait-states and read-while-write behavior — affects XIP performance and the
   MTD driver design (phase 4/5; `RTL:rtl/modules/rrc/`).
4. Whether boot1's `validate_image` accepts a payload spanning past the xous kernel slot
   up to `0x603D_A000` (expected yes — length field in sig block; verify in phase 4, else
   chainload trampoline).
5. IRQARRAY `*_dupe` routing discipline — which copy is canonical for S-mode Linux
   (cosmetic; any bank works since masks are per-bank).
